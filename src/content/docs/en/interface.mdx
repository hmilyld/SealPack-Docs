## Shortcuts

| Shortcut | Action |
| --- | --- |
| <Kbd>Ctrl</Kbd> + <Kbd>,</Kbd> | Open settings |
| <Kbd>Ctrl</Kbd> + <Kbd>W</Kbd> | Close the window |
| <Kbd>Alt</Kbd> + <Kbd>←</Kbd> / <Kbd>→</Kbd> | Previous / next wizard step |
| <Kbd>Esc</Kbd> | Close the context menu or dialog |
| <Kbd>↑</Kbd> <Kbd>↓</Kbd> <Kbd>Home</Kbd> <Kbd>End</Kbd> | Move focus in the tree and in menus |
| <Kbd>→</Kbd> <Kbd>←</Kbd> | Expand / collapse, step into / out of a folder |
| <Kbd>Space</Kbd> / <Kbd>Enter</Kbd> | Toggle the tree checkbox |

Inside a dialog, <Kbd>Tab</Kbd> cycles within the panel and <Kbd>Enter</Kbd> triggers the primary action.
<Kbd>Esc</Kbd> and clicking the backdrop both end the dialog properly; neither leaves the caller hanging.

<Callout tone="pitfall" label="Do not swallow Esc">

The global table runs in the **capture** phase on `window` and only calls `preventDefault` — it never
calls `stopPropagation`. Overlays (dialogs, the context menu) handle <Kbd>Esc</Kbd> themselves; if the
global table swallows it, the dialog cannot be closed.

</Callout>

## Context menu

A desktop program has a context menu on right click. SealPack replaces WebView2's native menu with a
hand-drawn one that follows the current skin, keeps full keyboard semantics (<Kbd>↑</Kbd> <Kbd>↓</Kbd>
cycle, <Kbd>Home</Kbd> / <Kbd>End</Kbd> jump, <Kbd>Enter</Kbd> activates, <Kbd>Esc</Kbd> closes and
returns focus), and nudges itself back inside the viewport near edges.

| Where | Items |
| --- | --- |
| Project row | Open executable folder / open output folder / delete project |
| File tree | Check current results / select all / select none / clear selection and filters / rescan |
| Inputs and script area | Cut / copy / paste / select all |
| Run log | Copy all output / clear log |
| Theme button | Window material toggle (Mica Alt) |

## The window

- **Frameless, hand-drawn title bar**: minimise / maximise / close are drawn by the frontend, the bar
  drags the window, double-click toggles maximise. A frameless window loses Windows' own edge resizing,
  so **eight transparent hit zones** take over the four edges and four corners.
- **Window materials**: on Windows 11 with Mica Alt enabled, the title bar, sidebar and status bar go
  translucent while the content area stays opaque. Any of three gates failing drops back to a solid
  colour: `set_effects()` fails (Windows 10), the user disabled it (right-click the theme button), or the
  system has "reduce transparency" on. A `▾` on the theme button means the menu exists.
- **Window size and maximised state are remembered, position is not** — the window always opens centred,
  so a monitor you unplugged last time cannot hide it.
- The window is created with `visible: false`; the frontend shows it after "write skin → two rAF frames →
  `show()`", so startup never flashes a white background. Rust has a 1.5 s fallback so a script error
  cannot leave the window invisible.

## Two designs, three light/dark modes

One click on the switcher in the title bar changes the design live. Both designs **share the same DOM**;
the difference is 100% CSS.

| Design | Type | Accent | Default theme in manual mode |
| --- | --- | --- | --- |
| Swiss grid | Instrument Sans + JetBrains Mono | warm paper `#faf8f5` + vermilion `#d8332a` | light |
| Terminal | Chakra Petch + IBM Plex Mono | near-black `#05070a` + cyan `#35d6e8` / acid green `#a3e635` | dark |


<Figure src="/shots/25-terminal-wizard-tree.png" alt="The wizard and file tree under the terminal skin" caption="Terminal skin — the same DOM as the screenshots above, only the CSS differs" />

Light/dark has three modes, cycled by the theme button:
`auto (follow system) → dark → light → auto`.

The default is **auto** — a local program should respect the Windows app mode instead of deciding for
itself. The system value comes from `prefers-color-scheme` (WebView2 maps it to the Windows app mode), and
the UI follows live without a restart. Once you choose manually the system no longer overrides it, and
**each design remembers its own** light/dark setting, restored when you switch back.

<Callout tone="note" label="Why not fork the DOM">

Skin and theme live on `<html>` as `data-skin` / `data-theme` / `data-themeMode`. Dialogs and toasts hang
off `<body>` but switch at the same time, so there is no intermediate state where some elements still
wear the old skin. Forking the DOM per skin would start the two implementations drifting apart — and only
users would see it.

</Callout>
